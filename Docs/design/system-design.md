## 0. 원칙

> **의도해서 만들어 넣는 게 아니라, 시뮬레이션의 결과로 실제와 비슷한 모습이 저절로 나오게 한다.
> 최적화상 불가능한 경우가 아니면 셰이더/연출로 흉내내지 않는다.**

이 프로젝트는 샌드박스이고, 관찰 대상이 물리 그 자체다. 연출로 흉내낸 것은 관찰할 가치가 없다.

**우선순위**
```
1순위  시뮬에서 자연 발생                     ← 기본
2순위  물리량은 실제로 추적, 표현만 셰이더     ← 예: 부유물 → 흰 선
3순위  순수 셰이더                           ← 광학 · 알갱이 질감만
```

"셰이더로 하면 싸다"는 3순위의 근거가 될 수 없다. 비용을 근거로 대려면
실제 수치(셀 수 × 패스 × substep, 메모리)를 계산해 제시할 것.

**따름정리**: 손으로 그린 지형을 미리 "자연화"하지 않는다. 수직 절벽이 시작하자마자
무너지는 것을 보는 것이 콘텐츠다. 편집 모드는 "시간이 멈춘 플레이"일 뿐이다.

## 1. 게임 정의

| 항목 | 결정 |
|---|---|
| 장르 | **샌드박스.** 목표·점수·판정 없음. 시뮬레이션 충실도가 곧 게임 |
| 표현 | **격자 + 입자 하이브리드.** 터널·아치·덩어리 붕괴가 타협 불가 요구사항 |
| 스케일 | 성 2~3m, 터널 지름 25~40cm, 입자 지름 5cm, 해변 60m × 60m |
| 카메라 | 자유 카메라 (캐릭터 없음 → 캐릭터-입자 충돌 문제 회피) |
| 누적 | 성이 여러 채 남아 각자 마르고 무너진다. 보러 가는 것 자체가 콘텐츠 |
| 조작 | 연속 브러시. 도구 11종 |
| 엔진 | UE5 |

### 왜 하이브리드인가

`W`(수분) 하나가 구동하는 현상들(버티다 갑자기 무너짐, 양지쪽 벽이 먼저 감,
조석에 따라 최적 지점이 이동)은 하이트필드만으로 전부 나온다.
그러나 **터널·아치·덩어리 붕괴는 원리적으로 불가능**하다. 하이트필드는 셀당 높이가 하나뿐이라
오버행을 표현할 수 없고, 위에서부터 스르륵 녹는 붕괴만 가능하다.

### 기술 선택 — 접근 3 (분업)

```
격자 [A]  →  Niagara         휘발성이어도 되고 빨라야 한다
구조물 [B] →  커스텀 컴퓨트    영속적이어야 하고 정밀해야 한다
```

두 계층이 정반대 성질을 요구하므로 하나의 도구로 둘 다 하면 어느 쪽이든 손해다.

| 기각한 안 | 이유 |
|---|---|
| Niagara 올인 | 상태가 리컴파일·스트리밍·컬링에서 날아감 → **누적 요구사항과 충돌**. 중단점 없음. GPU→CPU 리드백이 느려 도구 11종 분기와 타일 관리에 부적합 |
| 커스텀 올인 | 초기 비용이 큼. 첫 화면까지 RDG 파이프라인을 먼저 넘어야 함 |

**대가**: 격자 → 구조물 전달이 1프레임 늦다. 60fps · 파도 2m/s에서 3cm 오차로
입자 반경보다 작지만, 초기에 실제로 확인할 항목.

## 2. 아키텍처

### 상태는 정확히 한 객체가 소유한다

```
        UEnvironmentClock  (CPU, Subsystem)
        조석 위상 · 태양 · 바람 · 습도 · timeScale
                  │  스칼라 몇 개를 uniform으로 방송
        ┌─────────┴─────────┐
        ↓                   ↓
   ABeachField         FSandParticleSim
   (GPU / Niagara)     (GPU / 커스텀 컴퓨트)
   격자 b d s W f v φ    입자 x v W φ + 제약
        │                   ↑
        └─── FFieldBridge ──┘
```

읽기는 자유, **쓰기는 소유자만**. 갱신 순서가 곧 정확성이므로
(문서의 패스 순서는 바꾸면 결과가 달라진다) 상태를 나눠 가지면 순서를 강제할 방법이 없다.

**바람·태양·조석·파도·지하수면은 하나도 객체가 되지 않았다.** 각각 float 하나,
벡터 하나, 또는 셰이더 함수 한 줄로 내려앉는다.

### `W`는 두 곳에 있고 그것은 중복이 아니다

격자 `W` = 해변 지반의 수분 / 입자 `W` = 플레이어가 퍼올린 모래의 수분.
서로 다른 물체의 상태다. `FFieldBridge`가 정의한 지점(바닥면 모세관 흡수, 파도가 적심,
물 붓기)에서만 교환된다. 이 구분이 없으면 **"지면은 젖었는데 그 위 성은 마르고 있다"** 가
표현되지 않는다 — 게임의 핵심 압박인데도.

### 실행 순서도 정확히 한 곳이 소유한다

Subsystem이 각자 Tick하면 순서를 보장할 수 없다. **Tick을 도는 객체는 하나뿐이다.**

```cpp
class UBeachSimDirector : public UWorldSubsystem, public FTickableGameObject
{
    virtual void Tick(float Dt) override
    {
        Clock->Advance(Dt);                    // 1
        Tools->Flush();                        // 2
        Field->Step(Dt);                       // 3
        Bridge->GridToStructure();             // 4  ※ 1프레임 지연 허용
        Particles->Step(Dt);                   // 5
        Bridge->StructureToGrid();             // 6  ※ 희소, 비동기
    }
};
```

### 스케일 상수

| 항목 | 값 | 근거 |
|---|---|---|
| 월드 | 60m × 60m | 조석 감쇠 길이 `L`≈5~10m의 6~12배 |
| 격자 | **1024²** (셀 5.9cm) | 설정값. 개발 중에는 낮춰 씀 |
| 입자 반경 | 2.5cm (지름 5cm) | 터널 30cm = 6입자 폭 |
| 입자 예산 | 총 30만 / 성 한 채 3천~2만 | 성 10채 누적 여유 |
| `timeScale` | **1×** (기본) | **디버그·테스트용 설정값.** 아래 §시간 참조 |

**1024²를 고른 이유**: 발자국 4셀 · 해자 5셀 · 손가락 글씨 가능, 그리고
**셀 5.9cm ≈ 입자 지름 5cm** 라 격자↔입자 전환 손실이 사실상 사라진다.
비용은 스텝당 940만 스레드 · 메모리 100MB(핑퐁 포함) · CFL 여유(dt < 27ms)로 substep 불필요.

### 수치 타입 — 시뮬은 float, 엔진 경계만 double

UE5는 좌표를 double로 바꿨다(LWC). `FVector`는 double3이고, float3는 `FVector3f`다.
그러나 **LWC는 원점에서 km 떨어진 오픈월드를 위한 장치**이고 이 월드는 60m다.

```
float의 표현 간격 ≈ 값 × 1.2e-7
  → 월드 끝 6,000uu 에서 0.0007uu (7μm) = 입자 지름 5cm의 1/7000
```

| 대상 | 타입 | 근거 |
|---|---|---|
| 입자 `x v W φ` · 제약 · 격자 전 채널 | **`float` / `FVector3f`** | 필요 정밀도의 1만 배 여유 |
| 엔진 API 경계 (Actor 트랜스폼 · 트레이스 · 디버그 드로우) | `FVector` (double) | 호출 수가 적어 변환 비용이 무의미 |
| 누적 스칼라 (`RealTime`, `SimTime`) | **`double`** | float은 값이 커지면 `dt`를 통째로 삼킨다 |

**float을 고른 진짜 이유는 정밀도가 아니라 처리량이다.**

```
입자 30만 · 배열 하나      double3 7.2MB    vs  float3 3.6MB
SIMD (AVX2)               double 4폭       vs  float 8폭        → 2배
GPU double (M0-b)         float의 1/32~1/64                    → 사실상 선택지 없음
```

XPBD는 연산보다 **메모리 대역폭에 묶이므로 배열 크기가 곧 성능이다.**

### ★★ 시간 — 전부 1×. 압축하지 않는다

> **이전 결정(비균일 25×)을 폐기했다.** 근거는 아래. `sessions/26.09.04-research.md` §4-⑪에도 기록.

#### 왜 균일이어야 하나
**균일 배속은 물리를 안 바꾼다 — 단위 변환일 뿐이다.**
모든 rate를 S배 하면 모든 시간이 1/S가 되고 **길이 스케일은 보존된다.**
```
L = √(2KD/nω) 에서 K와 ω를 둘 다 S배 → 약분 → L 보존
```
**균일 배속 = 타임랩스 영상.** 실제로 일어난 일을 빨리 돌려보는 것이라 물리적으로 정직하다.
**비균일은 어떤 실제 상황의 타임랩스도 아니다.** 그런 해변은 지구에 없다.

#### 비균일 25×가 실제로 깨뜨리던 것
```
L = √(2KD/nω) 에서 ω만 25× 되고 K는 1× 이면

실제:     ω=1.405e-4, K=5e-4  →  L = 6.9 m
25× 조석: ω=3.51e-3,  K=5e-4  →  L = 1.4 m      ← 1/5로 압축
```
지하수면 구조가 **7m 띠에서 1.4m 띠로** 줄어 exit point 전이를 플레이어가 못 읽는다.
**세립사를 배제했던 이유(`L`=2m라 전이가 안 보임)를 배속으로 다시 만들어내는 셈.**

#### 그리고 압축이 필요 없다 — 1×에서 다 보인다
중조(조차 1.8m) 반일주조, 중간 조위, 해변 경사 1:10 기준:
```
수직 변화 0.45 m/시간  →  물가 이동 4.5 m/시간
```
**한 시간에 물가가 4.5m 움직인다.** 명백히 보인다.

| 프리셋 | 조차 | 물가 이동 |
|---|---|---|
| 극대조 (서해) | 9 m | **22 m/시간** — 무섭게 들어옴 |
| 중조 (캘리포니아) | 1.8 m | 4.5 m/시간 |
| 미소조 (동해) | 0.3 m | 0.8 m/시간 — 거의 안 변함 |

> **★ 25×를 곱하면 미소조도 19 m/시간이 되어 모든 프리셋이 다 극적으로 변한다.**
> `tidalRange`를 30배 차이로 세팅해놓고 배속으로 다시 뭉개는 셈 — **압축이 지역 차이를 지운다.**

**건조도 마찬가지.** 실제 표면 건조는 **15~30분**(더운 날)이고 구조적 약화가 1~3시간이다.
1시간 세션이면 표면이 2~4번 마른다 → 물을 다시 뿌린다 → **적절한 압박.**
25×면 표면 1분·붕괴 2~7분이라 **물 나르기만 계속하는 아케이드**가 된다.
실제로 사람들이 하는 행동은 "가끔 물 뿌리기"이지 1분마다 뛰어다니는 게 아니다.

#### 전부 1×
| 프로세스 | 특성 시간 | 배속 | 1×에서 세션 안에 보이나 |
|---|---|---|---|
| 파도 · swash | 5~10초 | **1×** | 끊임없이 |
| 침투 · 배수 | 초~분 | **1×** | uprush/backwash 비대칭이 살아남 |
| 입자 물리 | ms | **1×** | |
| 증발 · 건조 | 표면 15~30분 | **1×** | 1시간 세션에 2~4번 |
| 모세관 재분배 | 시간 | **1×** | |
| 지하수면 확산 | 시간 | **1×** | `L` = 6.9 m 보존 |
| 조석 · 태양 | 12.4시간 | **1×** | 물가가 시간당 4.5 m |

#### 세션보다 긴 것은 압축이 아니라 "선택"으로
```
대조소조 14.8일 / 계절 / 폭풍 사이클 며칠
   → 세션 시작 시 뽑는다 (이미 정한 방식). 압축 불필요
```

#### 기다림은 건너뛰기로 — 그것도 균일 배속
```
"물이 빠질 때까지" → 균일 고배속(×100)으로 고속 적분 + 진행바
                    화면은 전환/디졸브. 어차피 안 본다
```
**건너뛰기 중에도 균일이면 여전히 타임랩스다** — 파도가 0.07초가 되지만 안 보니 무관.
비용: 3시간 건너뛰기가 하이트필드 기준 대략 20~60초 계산. 진행바 하나면 된다.

#### `timeScale`의 위치
**설정값으로 남기되 기본 1×.** 디버그·테스트·트레일러용이며,
**건드리면 물리가 아니라 "빨리 감기"라는 것**을 명시한다.
비균일 배속은 다시 도입하지 않는다.

> **세션이 짧은 플레이어는?** 샌드박스는 원래 오래 앉아 있는 장르다.
> 짧게 하고 싶으면 **세션 시작 조건을 고르면 된다** — "밀물 시작", "폭풍 직전",
> "한낮 뙤약볕". **압축이 아니라 시작점 선택으로 해결하는 게 깔끔하다.**

## 3. 격자 계층 (해변)

### 객체 5개 — 실행 주체는 둘뿐

| 이름 | 형태 | 소유 |
|---|---|---|
| `UEnvironmentClock` | Subsystem | `RealTime`, `SimTime`, `TidePhase`, `SunDir`, `WindSpeed`, `WindDir`, `Humidity`, `timeScale` |
| `ABeachField` | Actor | Niagara 인스턴스 + RT 세트. 격자 상태 전체 |
| `USandPreset` | DataAsset | **입력 4개** → 물성 전부 파생 |
| `UWaveClimate` | DataAsset | 파랑 파라미터 |
| `UBeachLayout` | DataAsset | 초기 지형 |

`GroundwaterModel`, `WaveDriver`는 상태가 없어 **셰이더 안의 함수**가 되었다.

### 채널 패킹

```
RT_A (RGBA32F)   b(지형)    d(물깊이)   s(뜬모래)    W(수분)
RT_B (RGBA32F)   f_L  f_R  f_T  f_B                (4방향 유량)
RT_C (RGBA32F)   v.x  v.y  φ(공극률)   debris(부유물)
```

`φ`는 다지기 도구 때문에 추가(다지면 `φ`↓ → `K`↓ + 강도↑).
`debris`는 swash mark를 위한 것 — 아래 참조.

### 패스 순서 (스텝당 9개)

```
0. 도구 스탬프 소비      브러시를 b, W, φ에 적용
1. 파도 주입             경계 셀 수면 = 이봉 스펙트럼 합 + tide + setup
2. 가상 파이프           f += dt·A·g·Δh/l → K로 클램프
3. d 갱신 → v 산출
4. 침식/퇴적             C = Kc·max(sinα,minSlope)·|v|²·(1+exposure)   ★
5. 이류                  s, debris를 v 따라 반라그랑주 이동
6. 수분 W                지하수 평형 · 침투 · 배수 · 증발(2단계) · 모세관
7. 열침식                이웃 경사 > talus(W) 이면 아래로
8. 출력 패킹             RT export
```

**전 패스가 같은 `dt`로 돈다.** 시간이 하나뿐이라 격자 위 모든 채널이 일관된다.
(이전에는 6만 25×로 돌리려 했으나 지하수면 감쇠 길이가 1/5로 깨져 폐기 — §시간 참조)

### ★ 지하수면을 하이트필드에 넣는 법

문서는 "지하수면 아래 셀은 `W=1` 강제"라고 했으나, 하이트필드는 셀당 `W`가 하나뿐이라
깊이 방향이 없다. 대신 **지표에서 지하수면까지의 거리**로 평형 수분을 정의한다.

```hlsl
float waterTable   = h_mean + A*exp(-x/L)*sin(w*t - x/L) + superElevation;
float depthToWater = b - waterTable;                            // 음수면 잠김
float W_eq = saturate(1.0 - depthToWater / capillaryFringe);    // 모세관 상승대
W = lerp(W, W_eq, relaxRate * dt);
// 그 위에 침투 · 배수 · 증발이 교란을 준다
```

이 네 줄에서 전부 나온다.
- **exit point** = `depthToWater ≈ 0` 등고선. 별도 계산 없음
- **seepage face** = `W_eq ≈ 1`인 좁은 밴드 (물가 조금 위의 질척한 띠)
- 조석이 진행하면 exit point가 해변을 가로질러 이동 → 세션의 리듬
- **우물**: 구덩이를 파면 `b`가 낮아져 `depthToWater`가 음수 → 물이 차오른다.
  뒤쪽일수록 깊이 파야 하고, 썰물엔 우물도 마른다

### 파도 — 이봉 스펙트럼

`gamma`는 지역 상수가 아니고, 너울은 JONSWAP으로 표현되지 않는다 (papers G-6c).

```cpp
class UWaveClimate : public UDataAsset
{
    float Hs;              // 유의파고 — 위험도
    float Tp;              // 풍파 첨두 주기 — 폭풍까지의 거리
    float Dir;
    float SwellFraction;   // ★ 0~1. 하와이 0.9 / 동해 0.3 / 서해 0.0
    float SwellTp;         // ★ 너울 주기 11~16s

    static constexpr float Gamma      = 3.3f;   // 고정. 손대지 말 것
    static constexpr float BreakerIdx = 0.78f;  // H = 0.78·h
    static constexpr float SetupCoef  = 0.18f;
    static constexpr int   N          = 32;
};
```

**세트는 만들지 않는다.** 주파수가 다른 성분들의 맥놀이에서 저절로 나온다.
파고 Rayleigh 분포 · 파군 · wave setup · 장주기파가 전부 공짜로 따라온다.

```cpp
// 초기화 — 랜덤은 여기 딱 한 번
for (int i = 0; i < 32; i++) {
    F[i]     = fMin + (fMax-fMin) * (i + Rand01()) / 32;   // ⚠ jitter 필수
    A[i]     = sqrt(2 * BimodalSpectrum(F[i], ...) * df);
    Phase[i] = Rand(0, TWO_PI);
}
// 매 프레임 — 경계 셀 하나
float surface = SeaLevel + Tide + Setup;
for (int i = 0; i < 32; i++) surface += A[i] * sin(TWO_PI*F[i]*t + Phase[i]);
```

> ⚠ **jitter를 빼먹으면 160초마다 똑같은 파도가 반복되고 플레이어가 알아챈다.**

랜덤이 초기 위상 32개뿐이라 **시드 하나로 파도가 완전히 재현된다** → 저장/로드에 유리.

**게임 메커니즘으로 직결되는 것**: `swashReach = 1.25·√Hs·T`

| 심해 파고 | 주기 | 수평 도달 |
|---|---|---|
| 1m | 6s (풍파) | 7.5m |
| **1m** | **14s (너울)** | **17.5m** |
| 2m | 6s | 10.6m |

**2m 풍파보다 1m 너울이 두 배 이상 멀리 온다.** 겉보기엔 잔잔한데 물이 훨씬 위까지 올라와
안전하다고 판단한 자리의 성을 먹는다. 파고가 아니라 주기를 읽어야 하는 게임이 된다.

### 지형 — 3계층 + 직접 그리기

```
① 지역 (Region)      모래 프리셋 × 파랑 기후 × 조석 범위 × 분위기
② 지형 (Layout)      직선 / 만 / 곶 / 사주
③ 직접 그리기         게임 내 도구를 그대로 씀
```

지형 편집기는 새 시스템이 아니라 **이미 만들 브러시의 재사용**이다.
따라서 편집 모드와 플레이 모드의 구분이 사실상 없다 — 차이는 브러시 크기와 일시정지뿐.

**만(灣)을 넣으면** 굴절이 살아난다(곶에 에너지 집중, 만에 분산). 별도 구현이 필요 없다 —
가상 파이프가 얕은 곳에서 파도를 느리게 만들므로 천수·굴절이 근사적으로 저절로 나온다.
뒤로 물러나는 것(마름·바람) 말고 **옆으로 피하는** 선택지가 생긴다.

- 자연화(열침식 미리 돌리기)는 **선택 도구**. 기본은 "그린 그대로 시작"
- `bFollowEquilibrium` 같은 강제·경고 없음. 파도가 몇 주기 안에 알아서 깎는다
- Dean 평형식은 초기값 생성기일 뿐, 강제 대상이 아니다
- 바다쪽 경계 밴드만 편집 잠금 (파도 주입 조건)

void StampTool(const FToolStamp&);                 // 쓰기 — 유일한 통로

### 시각적으로 보이는 것들의 담당

```
5.9cm 이상  →  시뮬이 만든다 (진짜로 지형이 바뀜)
5.9cm 미만  →  셰이더가 만든다 (광학 · 알갱이 질감만)
```

| 현상 | 담당 | 근거 |
|---|---|---|
| berm · 세굴 · 프로파일 재편 | 시뮬 | `b` |
| **젖은 자국** (어두움) | 시뮬 | `W` — 추가 작업 0 |
| **swash mark** (흰 선) | 시뮬 | `debris` |
| rill (물길 자국) | **시뮬 (검증 필요)** | 수력 침식 채널화 + seepage |
| ripple (잔물결) | **시뮬 (검증 필요)** | 아래 |
| 포말 · 굴절 · 알갱이 질감 | 셰이더 | 광학 |

**젖은 자국 vs swash mark는 다른 것이다.**

| | 젖은 자국 | swash mark |
|---|---|---|
| 정체 | 물이 스며든 **면** | 부유물이 남은 **선** |
| 색 | 어두움 | **밝음** |
| 마르면 | 사라짐 | **남음** |

그래서 `W`로는 표현할 수 없다. `debris`를 **실제 물질로** 추적한다 —
물에 실려 이동하고, 침강 속도가 거의 0이라 물이 빠지면 표면에 남는다.
겹친 아치도, 다음 파도가 지우는 것도, **성에 걸려 쌓이는 것도** 저절로 나온다.

**ripple** — Nishimori & Ouchi(1993) 사구 모델은 두 단계뿐이고, 우리는 이미 둘 다 갖고 있다
(saltation ≈ 이류 / avalanche ≈ 열침식). 빠진 것은 **높이 의존성** 하나:

```hlsl
float exposure = (b - avgNeighborB) / cellSize;         // 이웃 높이차는 열침식에서 이미 계산 중
C           *= (1 + exposureGain * saturate(exposure)); // 돌출부가 더 깎이고
hopDistance *= (1 + exposureGain * saturate(exposure)); // 더 멀리 운반된다
```

돌출부가 깎여 뒤에 쌓이고 그게 새 돌출부가 되는 되먹임에서 파장이 자기조직화한다.
격자에서 나올 수 있는 최소 파장은 4~6셀 = **24~35cm**로 소형 리플(5~15cm)보다 크지만,
그 크기대는 **메가리플이라는 실재하는 현상**이고 60m를 내려다보는 화면에서는 오히려 잘 보인다.

## 4. 구조물 계층 (모래성)

### 소유권 단위는 "성"이 아니라 공간 타일

의미론적으로 "성 한 채"를 묶으려면 매 프레임 이런 판단이 필요하다 —
3m 떨어지면 별개인가? 이으면 합쳐지나? 굴러 나간 덩어리는 아직 그 성인가?
전부 임의의 임계값이고, 전부 틀릴 수 있고, GPU 연결 요소 분석이 매 프레임 필요하다.

**대신 해변을 4m × 4m 타일로 미리 쪼갠다. 입자는 자기가 있는 타일에 속한다. 그게 전부다.**

```
60m 해변 = 15 × 15 = 225 타일 (대부분 비어 있음, 희소 저장)
```

- 성이 경계에 걸치면 두 타일에 나눠 담긴다. 이웃 탐색이 경계를 넘으므로 물리적으로는 하나
- 붙여 지으면 자동으로 이어지고, 굴러가면 자동으로 다른 타일이 된다
- **"언제 새 구조물인가"라는 질문 자체가 사라진다**
- XPBD 이웃 탐색에 어차피 공간 분할이 필요하므로 **이미 필요한 자료구조의 재사용**이다

"성"은 시뮬레이션에 존재하지 않는다. 플레이어 머릿속에만 있다 — 샌드박스니 그걸로 충분하다.

### 객체 4개

```cpp

USandTileGrid      Subsystem. 15×15 희소 배열. 수명·예산·깨우기 판단 (CPU)

```

데이터 / 정책 / 계산 / 경계로 갈린다.

### 입자 상태

```
pos           float3   12    (x, y, z)
vel           float3   12    (x, y, z)
W             float     4    스민 수분. 그 자리에 머물고 모세관으로 천천히 퍼진다
surfaceWater  float     4    표면을 타고 흐르는 물. 중력 방향으로 흘러내린다

                       ──
                       40
```

`W`와 `surfaceWater`를 나누는 이유: **첨탑에 물을 부으면 기단이 과포화되는** 현상은
표면을 흘러내리는 물이 있어야 나온다. 스민 물은 흘러내리지 않는다.

**메모리 (20만 입자 기준)**
```
입자 상태        8.0 MB
점착 결합 목록   9.6 MB   ★ 가장 큼 — 아래 참조
정렬 버퍼        5.0 MB
예측 위치(임시)  2.4 MB
                ────────
                25 MB       격자(100MB)보다 작다
```

점착 결합은 **입자 상태가 아니라 별도 버퍼**다. "한 번 붙으면 남는" 목록이므로
어딘가 저장해야 하고, 매 프레임 이웃 탐색으로 다시 만들면 재결합이 일어나
"무너진 성은 안 돌아온다"가 깨진다.

```
입자당 최대 결합 12개 × 인덱스 4바이트 = 48 바이트
```
> 최밀 충전에서 접촉 이웃은 평균 6~8개라 12는 여유가 있지만, 다지기로 `φ`를 낮추면 늘어난다.
> 넘치는 결합은 버려지고 그 방향으로 성이 약해진다. **프로토타입에서 실제 분포를 볼 것.**

안 넣는 것들: 질량·반경(전부 균일 → 상수) / 법선·표면 여부(이웃 수로 매 프레임 계산) /
예측 위치(프레임 내 임시 버퍼) / 나이 / **온도**(미결 참조)

### 이웃 탐색 — 정렬 기반 공간 해시

Niagara의 `Neighbor Grid3D`는 두 가지가 우리에게 걸린다.
`MaxNeighborsPerCell`이 고정이라 최밀 충전(≈0.64)에 가까운 모래에서 **조용히 잘리고**,
균일 격자라 빈 공간도 메모리를 먹는다(8×8×2m를 5cm 셀로 = 33MB, 실제 사용은 5% 미만).

직접 짜면 둘 다 풀린다.
```
① 셀 키   해시로 접어 테이블 크기를 입자 수에 비례하게 (충돌해도 거리 검사로 걸러짐)
② 정렬    radix sort (20비트 → 5패스, 20만 개에 0.1ms 미만)
③ 셀 범위 테이블   키가 바뀌는 지점. 한 패스, 완전 병렬
④ 이웃 순회       27칸의 [start, end) 구간
```
메모리 약 5MB, **활성 영역을 넓혀도 늘지 않는다.**
정렬은 프레임당 1회면 되고(입자가 셀 하나보다 덜 움직이면 유효), 제약 반복 10~20회는 재사용한다.
정렬 후 입자 데이터를 재배치하면 캐시 적중률이 크게 오른다.

**잠든 타일의 입자는 정렬 입력에서 아예 빠진다.** 성 10채가 서 있어도 정렬 대상은 지금 만지는 한 채뿐.

### XPBD 제약은 셋뿐

```cpp
// ① 접촉
C = |p_i - p_j| - 2r,   C >= 0

// ② 마찰 — 접선 이동을 클램프. ★ 안식각 34°가 파라미터가 아니라 결과로 나온다
Δt_corrected = clamp(Δt, μ(φ) · |Δn|)

// ③ 점착 — 끊어지는 것이 곧 덩어리 붕괴
C = |p_i - p_j| - d_rest,   컴플라이언스 α = 1 / cohesion(W)
```

모든 물성이 `W`와 `φ`에서 나온다.
```cpp
cohesion = cohesionMax(grainSize) * strengthCurve(W);   // B1 곡선
μ        = frictionBase * (1 + compactionBoost * (1 - φ/φ_loose));
```

`strengthCurve`의 **왼쪽 절벽이 가파른 것**이 중요하다(papers B1). 마르는 성이
서서히 약해지는 게 아니라 **버티다 갑자기** 무너진다.

> **★ M0 실측이 정한 것 (m0-log #24~#26)**
> - **워밍 스타트는 선택이 아니라 필수다.** 매 스텝 λ=0 에서 시작하면 접선 잔차가 크리프(0.08 cm/s)로 굳어
>   더미가 30초에 7cm 주저앉고, 안식각이 μ 가 아니라 반복 수를 따라간다. 직전 λ 를 속도 임펄스로 먼저 적용한다
>   (Catto 2005). GPU(M0-b)에서는 이웃 리스트에 λ 슬롯을 얹는 형태가 된다.
> - **`frictionBase` 는 유효값 ≈ 0.13.** 회전 자유도가 없는 구는 기하학적 맞물림이 마찰 위에 약 25° 를 얹는다.
>   문헌의 모래 μ(0.5~0.7)를 그대로 넣으면 60° 첨탑이 선다. (반복 90 기준 μ0.10→29° · 0.15→34° · 0.20→39°)
> - **예산은 34° 를 안 보고 정한다** (m0-spike §2-1-a): ss 1 × 반복 180 이 플래토. 낮은 μ 일수록 예산에 민감해
>   반복 90 은 −0.7°, 23 은 −3.6° 다. 서브스텝은 워밍이 있어도 예산을 태울수록 나빠진다. 위 "15반복"은 폐기.
> - 단분산 구는 **격자 바닥 위에서 결정화**한다. 거친 바닥은 무작위 흔들림(0.3R)이어야 한다.
> - **점착 결합 확정값 (m0-log #27~#29):** 인장만 · 영구 목록 · 형성 1.2d · 파단 1.3d · 강성 변형 2% + 힘 고원 ·
>   `BondStrength 3`(자기 무게 배수) → c ≈ 1.5 kPa (Terzaghi 절토 H_c 74~84cm). 슬롯 12 로 충분. 결합 λ 도 워밍.
> - **벽·형틀도 워밍 스타트 대상이다.** 벽만 빼면 상자 안 60cm 위 블록이 순환한다(#29) — #18 의 재판. 같은 계의 제약은 전부 같은 규약.

> 세 계층이 같은 구조다 — [리턴 매핑](../research/terms/return-mapping.md).
> MPM은 Drucker-Prager 원뿔로, XPBD는 마찰 클램프로, 하이트필드는 안식각으로
> "허용 영역 + 투영"을 한다. 격자와 입자가 물리적으로 일관되게 붙는 근거.

### ★ 점착 제약의 수명 — 덩어리 붕괴의 핵심

매 프레임 새로 만들지 않는다. **한 번 붙으면 목록에 남고, 늘어나면 끊어진다.**

```
붙는 조건    거리 < 2r·1.05 이고 양쪽 W가 임계 이상    ← ★ 도구가 놓거나 다질 때만 검사
끊는 조건    거리 > d_rest·breakStretch (≈1.3)         ← 매 프레임 검사
             또는  cohesion(W) → 0 (말라서)
재결합       ★ **자발적** 재결합 없음 — 도구가 개입하면 새로 생긴다
```

> ⚠ **"재결합 없음"은 "다시는 안 붙는다"가 아니다.** 규칙의 정체는 **두 검사의 시점 비대칭**이다.
> ```
> 끊기   매 프레임        물리가 일으킨다
> 붙기   도구 조작 시에만  플레이어가 일으킨다
> ```
> 손으로 밀어 붙이는 것은 **붙는다**(도구 조작이므로). 금지되는 건 아무도 안 건드렸는데
> 시뮬레이션이 스스로 되붙이는 것이다. 매 프레임 이웃 탐색으로 목록을 재생성하면 그게 일어난다.

> ★ **`breakStretch` 는 상수가 아니어야 한다.** 모세관 다리의 파단 거리는
> `S_rupt/R = (1+θ/2)·V*^(1/3)` (papers.md B2, Lian 1993) 이라 물의 양이 정한다.
> 환산하면 `breakStretch ≈ 1.05`(거의 안 젖음) ~ `1.29`(funicular 진입) 이고,
> **지금의 `1.3` 은 그 중 가장 젖은 끝값**이다. 상수로 두면 마른 쪽에서 결합이 물리보다 오래 버텨
> **과대 안정** 방향으로 틀린다 — ★덩어리 붕괴가 안 나올 위험. `strengthCurve` 를 손보기 전에 여기부터.
> ```cpp
> breakStretch = 1 + 0.5 * (1 + theta/2) * pow(V(W), 1.0/3.0);
> ```

**그래서 "물을 다시 부으면 강도는 회복되지만 이미 무너진 형상은 안 돌아온다"가 나온다** —
`cohesion(W)`가 회복되면 **남아 있는** 결합은 다시 강해지고, 삭제된 결합은 안 돌아온다.

**물리와 어긋나는 지점을 정확히 해 둔다.** `1.05`(붙기) vs `1.3`(끊기)의 비대칭은
모세관 다리의 실제 이력 그대로다 — 거의 닿아야 생기고, 늘어나며 버티다 훨씬 멀리서 끊어진다
(Lian, Thornton, Adams 1993). 근사인 것은 **"언제 검사하나" 하나뿐**이고,
실제 모래도 무너지며 충전 구조와 결합 방향의 정렬이 깨져 되붙인 것은 원래보다 약하다
(remoulded strength). **방향은 맞고 정도가 과장된 근사.**

> 재결합을 매 프레임 허용하면 **붕괴가 부슬부슬로 수렴한다** — 끊긴 결합이 바로 다시 붙어
> 균열이 자라지 못하고 파단면이 안 생긴다. [순차 파단](../research/terms/progressive-failure.md)이
> 죽으면 ★덩어리 붕괴도 같이 죽는다. **성능 규칙이 아니라 핵심 요구사항을 지키는 규칙이다.**

그리고 끊어질 때 **연쇄**한다 — 한 층이 끊어지면 하중이 아래로 몰리고 그게 다음 층을 끊는다.
덩어리째 떨어져 나가는 것이 별도 로직 없이 여기서 나온다.

### 타일 상태 전이 — 두 개면 충분하다

```
활성(Active) ──정지 2초──▶ 잠듦(Sleeping) ──파도가 파괴──▶ 격자 환원
    ▲                          │
    └── 깨우기: 도구 접촉 / 파도 도달 / 이웃 타일 각성 ─┘
```

| 상태 | 입자 | 시뮬 비용 | 형태 |
|---|---|---|---|
| 활성 | 시뮬 중 | XPBD 15반복 | — |
| **잠듦** | 메모리에만 | **0** | 보존 |
| (격자 환원) | 사라짐 | — | **소실** |

**격자 환원은 파도가 실제로 파괴해 씻어갈 때만** 일어난다 — 그때는 형태가 어차피 없어진다.
하이트필드는 오버행을 표현할 수 없으므로 환원은 곧 터널·아치의 소실이고,
그래서 그 외의 이유로는 환원하지 않는다.

> **동결(Frozen)은 1차 범위에서 뺀다.** 입자를 해제하고 정적 메시로 굽는 상태를 검토했으나,
> **잠듦만으로 이미 시뮬 비용이 0**이라 동결이 추가로 주는 것은 입자당 76바이트뿐이다
> (성 10채 ≈ 3만 입자 → 2.3MB). 그 2MB를 위해 메시화·복원 파이프라인·상태 전이를 하나 더 만들고,
> 복원 시 점착 목록 재구성이 "재결합 없음" 원칙과 부딪히는 문제까지 떠안을 이유가 없다.
> 성이 100채쯤 쌓여 실제로 메모리가 문제가 되면 그때 붙인다. 예산 정책 자리만 확보해 둔다.

### 고정 스프레이(PVA) — 자원 관리가 아니라 물리다

실제 PVA는 **표면 수 mm에 얇은 막**을 만들어 알갱이를 붙인다. 속은 그대로다.

```cpp
cohesion = fixed ? cohesionMax : cohesionMax * strengthCurve(W);   // W와 무관하게 유지
if (waveStress > peelStress) fixed = false;                        // 파도가 막을 벗긴다
```

| 위협 | 결과 |
|---|---|
| 건조 · 바람 | 막음 |
| **파도** | **막이 벗겨짐** |
| 플레이어 도구 | 뚫림 (다시 작업 가능) |

**막이 벗겨지는 순간 진짜 `W`에 따른 강도로 돌아간다.** 그런데 고정해둔 성은 대개
오래 방치된 성이고, 즉 속이 이미 말라 있다.

```
파도가 껍질을 벗김 → 속은 W ≈ 0 → strengthCurve의 왼쪽 절벽 → 즉시 와르르
```

파도가 성을 조금씩 깎는 게 아니라 **한 번 때리면 껍질이 벗겨지고 그 아래가 통째로 무너진다.**
연출이 아니라 두 규칙(막 벗겨짐 + 마른 모래의 급격한 붕괴)이 만나서 나오는 결과다.

→ "뒤쪽에 지어 고정하면 오래 남고, 앞쪽 성은 결국 바다가 가져간다."

### `FFieldBridge` — 양방향

**격자 → 구조물** (매 프레임, 1프레임 지연 허용)
```
1. 파도 하중    d, v를 읽어 잠긴 입자에 항력.  τ ∝ ρ·|v|²
2. 수분 공급    d > 0인 셀 위의 입자 W 상승 / 바닥면은 격자 W와 모세관 평형
3. 증발         노출 입자에 2단계 건조 (태양 · 바람 · 그늘)
4. 지면 충돌    입자가 격자 b 아래로 못 내려감
```

**구조물 → 격자** (희소, 비동기)
```
1. 파괴 환원      점착이 다 끊기고 물에 실려간 입자 → 격자 s로 넘김. 입자 삭제. 질량 보존
2. 그림자 마스크   성이 드리우는 그늘 → 격자 증발률 감소
3. ★ 장애물 마스크  입자를 격자에 투영해 b_struct 생성.
                  물 흐름의 유효 지형 = b + b_struct
```

**3번이 없으면 물이 성을 통과해 지나간다.** 격자 물 흐름은 `b`만 보는데 성은 입자라
격자에 존재하지 않기 때문. 넣으면 따라오는 것이 전부 자동이다:
- 성 옆으로 물이 몰리며 속도가 붙음 → **옆과 뒤에 세굴 구덩이**
- 앞쪽은 물이 막혀 느려짐 → 퇴적
- **세굴이 기단을 파내면 성이 주저앉는다** ← 파도가 직접 부수는 것 말고 두 번째 파괴 경로

> ⚠ `b_struct`는 **침식 대상이 아니다.** 침식은 `b`에만 적용하고 성의 파괴는 입자 쪽에서
> 처리한다. 안 그러면 성이 격자와 입자 양쪽에서 이중으로 깎인다.

#### 장애물 마스크를 만드는 법

격자는 셀당 높이가 하나인데 입자는 3D다. **어떻게 눌러 담느냐가 터널의 운명을 가른다.**

| 방식 | 결과 |
|---|---|
| 셀 안 입자의 최대 높이 | 간단하지만 **터널이 막힌다** (지붕 높이가 벽이 됨) |
| 셀 안 입자 개수 → 밀도 | 터널은 뚫리지만 물리적으로 애매 |
| **바닥부터 연속으로 채워진 높이** | **터널이 뚫린다. 물리적으로도 옳다** ★ |

**물은 중력으로 아래에 있으니 물을 막는 것은 바닥에서 이어진 벽뿐이다.**
터널 위의 모래는 물 위에 떠 있는 지붕이고 흐름을 막지 않는다.

성 높이 2m ÷ 입자 지름 5cm = 40칸 → **`uint64` 하나**에 들어간다.

```hlsl
// 패스 A — 입자가 자기 셀의 자기 높이 칸을 켠다
uint2 cell = WorldToCell(pos.xy);
uint  slot = (uint)((pos.z - b[cell]) / slotHeight);   // 지면 기준
InterlockedOr(occupancy[cell], 1ull << slot);

// 패스 B — 바닥부터 연속으로 켜진 구간의 길이
b_struct[cell] = FirstZeroBit(occupancy[cell]) * slotHeight;
```

```
높이    점유                        200cm  ■ ← 지붕
                                     60cm  ■
b_struct = 30cm                      50cm  □ ← 터널
물이 30cm 위(터널)로 흐른다           40cm  □
                                     30cm  ■ ← 바닥부터 연속은 여기까지
                                      0cm  ■
```

물 흐름 반영은 유효 지형을 바꾸기만 하면 된다.
```hlsl
float terrainH = b + b_struct;
float dh = (terrainH + d) - (terrainH_n + d_n);
```

**비용**: `uint64` × 1024² = 8MB (전체를 다 잡아도). 활성 타일만 하면 4m 타일당 37KB.
잠든 타일은 형태가 안 변하니 캐시한다.

**한계 (수용)**: 하이트필드는 방향성이 없어 **막다른 터널에도 물이 통과**하고,
지붕이 물을 아래로 누르지 못한다. 고치려면 격자를 3D로 만들어야 해서 비용이 완전히 달라진다.

2번도 창발이다 — 성이 자기 그림자로 **자기 발밑 모래를 덜 마르게** 한다.
큰 성일수록 기단이 오래 버틴다.

### 지면과 구조물의 경계

**지면은 격자, 그 위 구조물은 입자.** 둘은 관통하지 않는다.
입자는 격자 `b`를 바닥으로 삼아 쌓이고, 파기 도구가 `b`를 낮추면 입자가 따라 내려온다.
해변에 판 구덩이는 격자가, 쌓아올린 성은 입자가 담당한다.

## 5. 도구 (11종) — 상세는 섹션 4에서

파기 / 쌓기 / **형틀** / 다지기 / 깎기 / **절단** / 터널 / 물붓기 / **분무** / **불기** / **고정**

> ★ **쌓기 브러시는 지나간 자리에서 붙는 조건을 한 번 돌린다** — 그러면 "쌓기"가 곧
> **"누르며 붙이기"** 가 되어, 플레이어가 무너진 것을 손으로 되붙일 수단이 M2부터 생긴다.
> (없으면 다지기가 오는 M6까지 성은 끊기기만 하고 붙지는 않는다 → m0-spike 미결 참조.)
> 코드는 이미 있는 생성 검사를 한 번 더 호출하는 것뿐이다.

굵은 것은 실제 모래 조각 도구를 조사해 추가한 것.

- **형틀(Form)** — 대형 작업의 실제 출발점("pound-up"). 원통 영역에 입자를 채우고
  `φ`를 낮춘 상태로 생성. 없으면 2m 성을 브러시로 한 삽씩 쌓아야 한다
- **절단(톱/철사)** — 깎기 브러시는 둥근 영역이라 평평한 면과 직선 모서리를 못 만든다
- **불기(빨대)** — 깎아낸 느슨한 입자를 날린다. 실제로도 손이나 붓으로 쓸면 표면이 상해서 분다
- **고정(PVA 스프레이)** — 동결 트리거

### 물 붓기가 셋을 동시에 한다

```
① W 상승   → 강도 회복      (원하는 것)
② 충격     → 파이고 뭉개짐  (대가)
③ 과포화   → 일시적 약화    (너무 부으면)
```

**②는 별도 로직이 필요 없다.** 임펄스 → 점착 제약이 늘어남 → `breakStretch` 초과 → 끊어짐 → 파임.

```
양동이 5L를 2초에, 1m 낙하 → F = ρ·Q·v ≈ 11 N
표면 입자 ~12개에 분산 → 입자당 1 N, 입자 질량 0.1kg → 가속도 ≈ 10 m/s²
```
**중력만큼의 힘이 위에서 한 번 더 누르는 셈.** 잘 다져진 젖은 성은 버티고,
마르기 시작한 성이나 얇은 첨탑은 파인다.

브러시 세기 = 유량 = 충격이므로 **조절이 곧 기술**이 된다(콸콸 / 살살 / 분무).
커서 높이를 낙하 높이로 쓰면 `√(2gh)` 배율이 한 겹 더 붙는다.

③은 배수로 회복된다 — 과잉 수분이 빠져 `fieldCapacity`로 수렴하고 그게 최적 강도 근처다.
**부은 직후가 가장 약하다.** 물을 주고 잠깐 기다렸다가 작업해야 한다.

```cpp
struct FWaterPour { FVector Center; float Radius; float FlowRate; float DropHeight; };
```

**흘러내림**은 1차 범위. 입자에 "표면수" 스칼라 하나 + 중력 방향 이웃에게 전달하는 패스 하나.
첨탑에 물을 주면 기단이 과포화된다.

## 6. 렌더링

### 6-1. 물은 표면 재구성이 필요 없다

화면공간 유체 렌더링(van der Laan 2009)이 푸는 문제는 **"점 구름에서 표면을 어떻게 만드나"** 다.
우리 물은 점 구름이 아니라 격자다.

```
물 표면 높이 = b + d        ← 셀마다 높이가 하나. 이미 표면이 정의되어 있다
```

지형과 **완전히 같은 방식**으로 그린다 — 평면 메시를 하나 더 깔고 `b + d`로 WPO 변위,
`d ≈ 0`인 곳은 그리지 않는다. 그 기법은 읽어둘 가치는 있으나 이 프로젝트에서는 쓰지 않는다.

> 용어 혼동 주의: **화면공간 굴절**(이미 그려진 씬 컬러를 노멀 방향으로 밀어 샘플링)은
> 별개의 기법이고 **이건 쓴다.** 물 아래 모래가 일렁여 보이는 것이 그것이다.

| 요소 | 근거 채널 |
|---|---|
| 표면 기하 | `b + d` → WPO |
| 얕은 물 경계 | `d`로 알파 페이드 (딱 끊기면 종이처럼 보인다) |
| 물 색 · 흡수 | `d` |
| **탁도** | `s` → 파도 끝자락의 갈색 물 |
| 굴절 | 노멀 + 화면공간 굴절 |
| **표면 흐름** | `v` → 플로우맵. 왜곡과 거품 줄무늬 |
| **포말** | `\|v\|` 큰 곳 마스크 |

별도 시뮬이 필요한 항목이 하나도 없다.

### ⚠ 쇄파 튜브는 포기한다 (비용 근거 있는 예외)

말리는 파도(plunging breaker)는 **오버행**이라 하이트필드로 원리적으로 불가능하다.
모래성 터널과 같은 문제인데 **결론은 반대**다.

**포기 비용**
```
전면 3D:  swash대 60m × 20m × 0.3m = 360 m³
          셀 5cm(튜브 표현 최소) → 288만 셀 → FLIP 입자 2,300만
          현재 GPU 실시간 한계(수백만)의 10배 초과

쇄파 띠만: 1.5m × 60m × 0.5m = 45 m³ → 36만 셀 → 약 290만 입자
          간신히 경계선. 그러나 경계에서 질량·운동량 보존이 어렵고,
          쇄파선이 매 순간 이동하므로 3D 영역이 파도를 따라다녀야 한다.
          물 입자는 비압축성 제약 때문에 모래보다 반복도 더 필요하다
```

| | 모래성 터널 | 파도 튜브 |
|---|---|---|
| 입자 수 | 20만 | **290만 ~ 2300만** |
| 요구 등급 | **타협 불가** | 시각적 장식 |
| 판단 | **비용을 지불했다** | **지불하지 않는다** |

그리고 우리 파고(0.4m)에서는 애초에 잘 안 생긴다 — 우리 입도는 plunging~surging 영역이고
**surging은 아예 안 부서지고 밀고 올라온다.** 큰 세트에서 잠깐 나오는 10~20cm 말림이 전부다.

**대신 2순위 해법**(원칙 §0):
```
① 시뮬이 쇄파 조건을 판정한다      H > 0.78·d 이고 |v|가 크고 d가 급격히 얕아지는 지점
② 그 지점에 쇄파 VFX를 스폰한다    물보라 · 거품 · 흰 마루
```
**위치 · 타이밍 · 세기가 전부 시뮬에서 나온다.** 말림 형태만 미리 만든 것이다.

### 6-2. 모래성 — 메시화

입자는 위치 20만 개일 뿐 표면이 없다. 그런데 GPU는 삼각형만 그린다.
그리고 **입자 지름 5cm vs 실제 모래알 0.5mm(100배)** 라 입자를 구로 그리면 자갈 더미가 된다.
점 구름 → 연속 표면 변환이 필요하다.

#### 방식 선택 — 메시화

성 한 채를 3m × 3m × 2m로 잡고 계산하면:

```
메시화       SDF 격자 셀 2.5cm(입자 반경) → 전체 115만 셀
             표면 밴드(±2셀)만 처리       → 약 20만 셀   ★ 실제 처리량
             셀당 이웃 입자 ~30개 순회    → 600만 연산, 밀리초 미만
             출력 약 7만 삼각형/채, 10채 = 70만 삼각형 · 메모리 20MB

             ★ 활성 타일만 갱신. 잠든 성 9채는 메시 캐시 그대로, 비용 0

화면공간     매 프레임 고정: 입자 20만 스프라이트 + 곡률 흐름 4~8회 × 200만 픽셀
             ★ 정지한 성이 있어도 비용이 안 줄어든다
```

| | 메시화 | 화면공간 |
|---|---|---|
| 정지 상태 비용 | **거의 0** | 매 프레임 전액 |
| **그림자 드리움** | **된다** | **안 된다** |
| 반사 · 루멘 | 잡힘 | 안 잡힘 |
| 시간적 안정성 | 안정 | 카메라 움직이면 출렁임 |
| 두께 기반 투과 | 불필요 | 강점이지만 **모래엔 무의미** |

**화면공간 방식의 최대 장점(정지 여부와 무관하게 싸다)이 우리에겐 오히려 손해고,
최대 단점(그림자)이 우리에겐 치명적이다.** 증발률이 `dot(n, sunDir) × shadowMask`에
비례하므로 그림자는 장식이 아니라 게임 메커니즘이다.

#### 파이프라인

```
① SDF 생성      입자 → 격자 splat. Yu & Turk 비등방 커널.
                활성 타일의 표면 밴드만
② 등위면 추출    Surface Nets → 삼각형 + 정점 노멀. 정점에 W, φ를 실어 보냄
③ 렌더          평범한 메시. 그림자 · 반사가 공짜
```

**비등방 커널이 필요한 이유** (Yu & Turk 2010): 입자를 등방 구로 보면 표면이 구들의
합집합이 되어 물방울처럼 울퉁불퉁해진다. 평평한 면이 물결치고 얇은 벽이 부푼다.
**절단 도구와 형틀로 만든 수직 벽이 곤죽으로 보이면 그 도구들이 무의미해진다.**
이웃 분포의 공분산을 고유분해해 커널을 방향에 따라 늘리면 평면은 평면으로, 얇은 벽은
얇게 나온다. 이웃 수가 적으면 구형으로 되돌아가므로 **깎아낸 부스러기는 덩어리로 보인다.**

> 논문은 매 프레임 전 입자에 대해 커널을 다시 계산한다(유체는 계속 움직이니까).
> **우리는 잠든 타일의 커널을 캐시할 수 있다** — 이 기법의 가장 큰 비용을 구조가 이미 회피한다.

**등위면 추출은 Surface Nets로 시작한다.** Marching Cubes는 모서리를 뭉개고 삼각형이 많다.
Dual Contouring이 모서리는 가장 날카롭지만 self-intersection · non-manifold 함정이 있다.
**실제 모래 모서리는 완벽히 날카롭지 않으므로**(알갱이 크기만큼 둥글다) Surface Nets로 충분할
가능성이 높다. 절단면이 눈에 띄게 뭉개지면 그때 DC로 올린다.

#### 재질

```
알베도 · 러프니스   f(W)          정점 W 보간 → 젖은 경계가 표면에 그대로 보인다
서브서피스          Burley SSS    젖은 모래의 속빛 (Christensen & Burley 2015)
알갱이 질감         디테일 노멀맵  ← 3순위 셰이더. 0.5mm는 원리적으로 불가하므로 정당
```

#### ⚠ 최대 리스크 — GPU 생성 메시를 UE5에서 그리기

```
UProceduralMeshComponent   CPU 기반. 20만 셀을 CPU로 돌리면 느리다
GPU 생성 + 간접 드로우      필요한 것. 삼각형 수가 동적이라 DrawIndirect가 필요하고
                           커스텀 FPrimitiveSceneProxy + Vertex Factory를 써야 한다
```
→ [렌더 스레드 / SceneProxy](../research/terms/render-thread-proxy.md) ·
[Vertex Factory](../research/terms/vertex-factory.md) ·
[간접 드로우](../research/terms/draw-indirect.md)

**★ 3단계 경로로 리스크를 미룬다**

```
1단계   입자 위치만 리드백(활성 타일 1채 = 3천 개 × 12B = 36KB)
        SDF도 Surface Nets도 CPU 멀티스레드
        UDynamicMeshComponent로 그리기
        → 렌더링 내부 지식 0으로 화면에 모래성이 나온다
        → W는 정점 컬러에 실어 우회

2단계   프로파일링. 정말 병목인가? 활성 타일이 1~2개면 안 걸릴 수도 있다
        (표면 밴드 20만 셀, 8코어 멀티스레드로 약 2.5ms)

3단계   병목이면 그때 GPU로 옮긴다 (Vertex Factory + 간접 드로우)
```

1단계에서 이미 게임이 돌아가면 3단계는 "되게 만드는 일"이 아니라 "빠르게 만드는 일"이 된다.
그리고 만들어봐야 진짜 병목이 어디인지 안다.

> ⚠ **SDF만 GPU로 하고 리드백하는 절충은 피할 것.** SDF 갱신 → 리드백 2프레임 →
> 메시 생성 → 화면 = 50~65ms 지연이라, 브러시로 문지르는데 표면이 늦게 따라와 손맛이 나쁘다.
> 1단계는 **입자 위치만 리드백하고 나머지는 전부 CPU**로 두어 지연을 없앤다.
