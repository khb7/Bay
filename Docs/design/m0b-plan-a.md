# M0-b A안 — 8색 블록 GS 계획

> **결과 (2026-10-26)** — 단계 0~2 통과 (#40 · #41 · #42), 단계 3 성능은 A안 단독으로 실패 (#43: 5만 반복 60 다짐 중 52.9 ms). 이후 깊은 더미가 끓는 문제(#44~46)를 접촉 매개변수 Kv 1 · Kc 0.2 (#47~48) 와 입자별 탐색 여유 `-pmargin` (#50) 로 풀어 **다짐 중 15~21 ms · 정지 16.3 ms** (#54). 블록 15cm 확정, 반복 60 고정 (30 은 터널 붕괴).


> 2026-10-24. 근거: m0-log #36 ④⑤ · #38 · #39. 원전: papers C5 (Harada 2011/2014 · Coumans 2013 · Bullet3 `b3Solver`).
> 상위 문서: [m0b-spike.md](m0b-spike.md) §3-1(물리 동등성) · §3-4(성능).

## 0. 왜 A 인가 — 한 줄씩

- 결합 터널이 선 것은 **접촉을 순차로 풀었을 때뿐**이다 (전부 순차 #36 ④, 블록 안 순차 #36 ⑤). 결합은 gather 로도 된다.
- 접촉을 동시에(gather) 풀면 반복을 늘려도(240), 질량 분할을 해도, APGD 로 수렴을 6배 올려도(#39) 터널은 무너진다. 다짐 상태가 GS 와 같아도(#39 `-apgdnobonds`, 블록 63.9cm) 무너진다.
- 지금 GPU 블록 방식(#38)은 **경계 접촉(20~35%)이 Jacobi 로 남아** 마른 더미가 기어가고, **스레드 하나 = 블록 하나 순차**라 느리다.
- A 는 두 결함을 한 번에 없앤다: 경계 접촉도 순차가 되고(진짜 GS), 블록 안도 병렬이 된다.

## 1. 알고리즘

### 1-1. 바깥층 — 블록 8색

- 공간을 한 변 B 의 정육면체 블록으로 나눈다 (지금의 정렬 해시 블록 그대로).
- 블록 좌표 (bx, by, bz) 의 색 = `(bx&1) | (by&1)<<1 | (bz&1)<<2` → 0~7.
  같은 색 블록끼리는 사이에 다른 색 블록이 하나 끼어 있어 **입자를 공유하지 않는다** (조건: B ≥ 접촉 도달거리 2R + 이동 여유. B 10cm 이상이면 충분).
- **접촉 소유권**: 접촉 (i, j) 는 `min(i, j)` 입자의 블록이 맡는다. 상대 입자가 이웃 블록(다른 색)에 있어도, 그 블록은 이 색 단계에서 쉬고 있으므로 안전하게 쓴다.
- 반복 1회 = 색 0 → 7 을 차례로 디스패치. 색 c 는 색 0~c−1 이 고친 결과를 본다 → 블록 단위 GS. **경계 Jacobi 가 없다.**

### 1-2. 안층 — 블록 안 접촉 컬러링

- 블록 하나를 워크그룹 하나(64~256 스레드)가 맡는다.
- 블록 안 접촉을 "같은 입자를 두 번 만지지 않는" 배치로 나눈다 (greedy 그래프 컬러링, 입자당 배치 비트마스크). Harada 의 실측으로 배치 10~15개.
- 배치 단위로 스레드가 접촉을 나눠 풀고, 배치 사이에 `GroupMemoryBarrierWithGroupSync`. 배치 안에선 입자가 겹치지 않으므로 **결과가 순차와 같다** (순서만 바뀐 GS).
- 컬러링은 프레임당 1회 (접촉 목록은 프레임 동안 고정, #3.5). 반복마다 다시 하지 않는다.

### 1-3. 나머지 — 바꾸지 않는다

- 결합: gather 그대로 (`SolveBondsCS` · `ApplyBondsCS`, #36 ④ 근거).
- 지면·벽: 입자별, 그대로.
- 워밍 스타트 1.0 필수 (#36 3-2) — 쌍 목록 λ 슬롯은 2단계 `-gpu2` 것을 쓴다.
- APGD 는 얹지 않는다. 모멘텀은 동시 방식용이고, GS 위에서의 효과는 미검증이다.

### 1-4. 반복 1회의 패스

```
색 0..7    SolveColorCS(c)     워크그룹 = 그 색의 블록 하나, 블록 안 배치 순서대로     × 8
결합       SolveBondsCS → ApplyBondsCS                                             × 2
지면·벽    (기존)                                                                  × 1~2
```

반복당 디스패치 ~12 (지금 블록 방식 ~6).

## 2. 단계와 관문

각 단계는 관문을 통과해야 다음으로 간다. 실패하면 §4 분기.

### 단계 0 — CPU 모사 `-color8` (반나절)

- `FSandSpike` 에서 접촉을 (색, 블록, 블록 안 배치) 순으로 정렬해 순차로 푼다. 이것은 **순서만 바꾼 GS**라 물리는 GS 와 같아야 한다.
- 목적: "순서가 바뀐 GS" 가 정말 GS 와 같은지 확인한다. GS 는 순서에 민감할 수 있다 (예: 블록 경계를 따라 생기는 띠 무늬).
- 관문: 더미 시드 3·1337 크리프 ≤ 0.005 · 침하 0 / 터널 원형 30cm 0% / 절토 H_c 84~95cm. 반복 120 · μ 0.17 (GS 기준과 같은 조건).

### 단계 1 — GPU, 색만 (2일)

- 지금의 블록 분류 counting sort 에 색 키를 붙여, 색마다 블록 범위를 낸다. 소유권 규칙(§1-1)으로 접촉을 블록에 배정.
- `SolveColorCS(c)`: 처음엔 **스레드 하나 = 블록 하나 순차** (지금 `SolveBlocksCS` 그대로, 경계 패스만 삭제). 물리 동등성을 먼저 본다.
- 관문: 단계 0 과 같은 수치 (더미·터널·절토). 2단계 `-gpu2` 경로 위에 얹는다.

#### 단계 1 상세 (2026-10-24, 코드 읽고 확정)

**바탕**: 2단계 `-gpu2` 경로(`FSandGpuSim` · `SandFrame.usf` · `SandSolver.usf`)를 고친다. 1단계 `-gpu` 경로는 건드리지 않는다. 옛 블록 방식은 스위치 뒤에 그대로 두어 대조군으로 쓴다.

**1-0. R1 디스패치 비용 측정 (구현 전, 1~2시간)**
- 지금 블록 방식으로 `-perf -gpu2 -particles=3000,20000 -frames=60` 을 반복 {1, 30, 120} 으로 돈다.
- `(T120 − T1) / 119 / 반복당 패스 수` = 패스 1회 비용. 3000개에서 ≫ 10 µs 면 GPU 일이 아니라 RDG·런치 오버헤드다.
- 판단: 회당 ≤ 10 µs → 그대로 진행. 크면 단계 1 은 그대로 짜되, 1-5 의 완화책을 단계 1 끝에 넣는다.

**1-1. 블록 키에 색을 박는다 — `CellKeyCS`**
- 지금: `BlockKey = HashCell(CellOf(P, BlockSize), BlockTable)` (8192칸 해시).
- 바꾼다: 블록 셀 좌표 `c` 의 색 `col = (c.x&1) | (c.y&1)<<1 | (c.z&1)<<2`, `BlockKey = col · (BlockTable/8) + HashCell(c, BlockTable/8)`.
- 그러면 기존 `Scan(BlockPairCount) → BlockStart` 한 번으로 **색 c 의 블록들이 [c·1024, (c+1)·1024) 연속 구간**에 놓인다. 새 정렬 패스가 필요 없다.
- 해시 충돌: 같은 색의 먼 두 블록이 한 칸에 묶이면 한 스레드가 순차로 둘 다 푼다 — 안전(지금과 같은 성질). 다른 색끼리는 구간이 달라 충돌하지 않는다.

**1-2. 접촉 소유권 — `PairFillCS`**
- 지금: `BKi == BKj` 면 블록 안, 아니면 경계(`0xFFFFFFFF`).
- 바꾼다: 쌍은 항상 `j > i` 로 생성되므로 **소유 블록 = BKi** (= min(i,j) 의 블록, 단계 0 규칙과 같다). 경계 쌍은 0 개.
- 안전 조건: 같은 색 두 블록 사이엔 최소 한 블록(B)이 끼므로, 한 입자를 두 블록이 동시에 만지려면 접촉 도달거리 `SearchRange` 의 두 배가 B 보다 커야 한다. `SearchRange ≈ D + 여유 ≈ 5~6cm` → **B ≥ 15cm 에서 안전**, 10cm 는 경계(쓰지 않는다). 프레임 중 이동(< 1cm)은 여유에 들어간다.

**1-3. 반복 루프 — `AddSolverIterations`**
- 색 모드: 반복마다 `for c in 0..7: SolveBlocksCS(BlockBase = ((c + Frame) & 7) · 1024, NumBlocks = 1024)` → `SolveBondsCS` → `ApplyBondsCS`(지면·벽 포함, 그대로).
- `CountBoundaryCS` · `SolveBoundaryCS` · `ApplyBoundaryCS` 는 건너뛴다. 질량 분할은 경계 gather 에만 쓰였으므로 꺼진다.
- `SolveBlocksCS` 에 `BlockBase` 매개변수 하나 추가 (`b = BlockBase + Tid.x`). 몸체는 그대로 — 이미 GS 다.
- 반복당 디스패치: 지금 6 → 10 (색 8 + 결합 2).
- 색 회전(`(c + Frame) & 7`)은 단계 0 의 R5 결과로 기본 켬. 프레임 번호는 `FSandGpuFrameParams` 에 추가.

**1-4. 배선**
- `FSandGpuFrameParams` 에 `bColor8` · `FrameIndex`. `FSandSpike::StepGpuResident` 가 `Params.bColor8` 이면 넘기고, `BlockSize` 는 0 이면 15.
- 커맨드릿: 기존 `-color8` · `-block=` 을 `-gpu2` 와 함께 쓴다. CPU 경로의 `OrderContactsColor8` 은 `bGpuResident` 면 건너뛴다(이미 `bGpuSolve` 조건과 같은 자리).
- 통계: `NumBoundary` 가 0 이어야 한다 — 색 모드 검증용으로 로그에 찍는다.

**1-5. R1 완화책 (1-0 결과가 나쁠 때만)**
- 반복 루프 전체를 **RDG 패스 하나** 안에서 `RHICmdList` 로 직접 디스패치 (UAV 배리어만 사이에) → RDG 패스 생성 비용 제거.
- 그래도 크면 반복 60 으로 내린 수치를 같이 기록한다 (단계 0 에선 120 만 검증 — 60 은 CPU 로 한 번 더 확인 필요).

### 단계 2 — GPU, 블록 안 병렬 (2~3일)

- 프레임당 1회 `ColorBatchCS`: 블록마다 워크그룹이 접촉을 배치로 나눈다 (groupshared 비트마스크).
- `SolveColorCS` 를 워크그룹 = 블록, 배치 단위 병렬로 바꾼다.
- 관문: 단계 1 과 같은 수치 + 성능 스윕(`-perf`)이 단계 1 보다 빠르다.

#### 단계 2 상세 (2026-10-24)

**바탕**: 단계 1 의 색 모드(`bColor8`) 위에 스위치 `-color8par` 를 더한다. 꺼지면 단계 1 그대로(대조군). 바뀌는 곳은 접촉 정렬 뒤 1 패스 추가와 `SolveBlocksCS` 대체뿐 — 결합·지면·벽·색 회전은 그대로.

**2-0. 기준선 측정 (구현 전)**
- 단계 1 로 `-perf -gpu2 -color8 -block=15 -particles=3000,20000 -frames=60 -iterations=120` → ms/프레임, 그리고 색 패스만의 시간(반복 1 vs 120 차).
- 이 수치가 단계 2 성능 관문의 비교 대상이다.

**2-1. 블록 안 배치 나누기 — `ColorBatchCS` (프레임당 1회)**
- 워크그룹 하나 = 블록 하나 (전 색 8192 블록 한 번에 디스패치. 입자 마스크는 블록마다 따로라 블록끼리 경쟁 없음).
- 그룹 안 **스레드 0 이 순차 greedy**: 블록 접촉을 원래 순서(k 오름차순)로 돌며, 두 입자의 마스크에서 처음 비어 있는 비트 = 배치. 단계 0 CPU `OrderContactsColor8` 과 같은 규칙 → **같은 풀이 순서**(CPU 와 대조 가능).
  - 입자 → 마스크는 groupshared 개방 주소 해시 (512칸 × {입자 id, 마스크} = 4KB). 반복당이 아니라 프레임당 1회라 순차여도 싸다 (블록당 접촉 수백 × 1회).
  - 해시가 넘치면 그 블록 플래그 = 순차 → 풀이 때 스레드 0 혼자 단계 1 방식으로 푼다 (안전한 후퇴). 넘친 블록 수를 통계로 센다.
- 배치 상한 `MaxBatch = 32`. 넘는 접촉은 마지막 배치(31)로 몰고 그 배치는 순차로 푼다.
- 출력:
  - `ContactOrder[k']` : 블록 구간 안에서 (배치, k) 순으로 늘어선 접촉 번호. λ 슬롯은 원래 k 그대로 → 워밍 스타트 불변.
  - `BatchStart[b · 33 + t]` : 블록 b 의 배치 t 시작 (8192 × 33 uint ≈ 1MB).
  - 배치 수 카운트 → 단계 0 과 같은 `[color8]` 통계(평균·최대 배치, 순차 후퇴 블록 수).
- 순서 재배치는 스레드 0 의 2회 훑기(배치별 개수 → 접두합 → 채우기). 블록 안에서 끝난다.

**2-2. 배치 병렬 풀이 — `SolveBlocksParCS`**
- `[numthreads(64,1,1)]`, 그룹 = 블록 (`b = BlockBase + GroupId.x`), 디스패치 1024 그룹 × 색 8.
- `for t in 0..nBatch-1: for k' = BatchStart+tid; k' < BatchEnd; k' += 64 → SolveContact(ContactOrder[k'])`, 배치 사이 `DeviceMemoryBarrierWithGroupSync()` (위치가 전역 UAV 라 Group 이 아니라 Device 배리어).
- 접촉 몸체는 `SolveBlocksCS` 의 것을 함수로 빼서 공유한다 (식이 둘로 갈라지지 않게).
- 배치 31(넘침)·순차 후퇴 블록: 스레드 0 만 순차.
- 빈 블록 그룹은 즉시 반환. 7/8 이 비거나 성긴 건 R3 — 2-4 에서 잰다.

**2-3. 배선**
- `FSandGpuFrameParams::bColor8Par`, 커맨드릿 `-color8par` (`-color8` 을 함께 켬).
- 버퍼 `ContactOrder`(쌍 용량) · `BatchStart` · `BatchStats` 를 `FSandGpuSim` 상주 버퍼로.
- `ColorBatchCS` 는 `PairFillCS`·블록 범위 계산 뒤, 반복 루프 앞에 1 회.

- 실행: GPU 측정은 **동시 1개**로 내린다 — 단계 1 더미 시드 3 이 2개 동시 실행 중 `DXGI_ERROR_DEVICE_HUNG`(TDR 2초) 로 죽었다. 성능 측정도 단독이어야 수치가 맞다.

**2-5. 작업 순서와 커밋 단위**

```
① 2-0 기준선                    → m0-log #42 수치
② 2-1 · 2-2 · 2-3 구현           → 커밋 1 (feat: A안 단계 2 — 블록 안 배치 병렬)
③ 관문 (물리 4종 + 성능)          → m0-log #42 결과 · 커밋 2
```

**위험**
- 배치 수가 많은 빽빽한 블록(최대 23)은 배리어 23회 × 반복 120 → 그룹 지연. 성능이 기대 이하면 블록 10cm 는 안전 조건(B ≥ 15) 때문에 못 줄이므로, 대신 그룹 64 → 32 로 점유율을 올려 본다.
- 블록당 접촉이 64 보다 훨씬 적으면 병렬 이득이 작다 — 3000개 시험에선 효과가 작고 2만 이상에서 봐야 한다.

### 단계 3 — 성능 판정 (1일)

- `-perf -color8par` 입자 수 {2만, 5만} × 블록 {15, 20cm} × 반복 {60, 120} + 15만 · 반복 120 기록 1회. 블록 10cm 는 안전 조건(B ≥ 15) 밖이라 뺀다.
- 판정 (2026-10-25 하향): **활성 5만 · ≤ 16 ms 통과**, 16~33 조건부, 33 초과 실패. 반복 60 이 이기면 물리 관문을 반복 60 으로 다시 돈다.
